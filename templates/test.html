Learning Muscle

Structure Charts

Structure charts are essential tools in software engineering, particularly for designing and documenting complex systems. They visually represent the breakdown of a system into subroutines and illustrate how these subroutines interact with one another. Here’s a detailed explanation of the symbols used in structure charts and their significance:

Symbols and Their Meanings

  1. Empty Circle:

    • Meaning: Indicates data movement between subroutines.
    • Usage: Typically used to show parameters passed between subroutines.
    • Library System Example: In the diagram, an empty circle is used between "Check book" and "Update files" to show that "Book details" are passed as parameters.

  2. Filled Circle:

    • Meaning: Represents a flag or control variable passed between subroutines.
    • Usage: Used to indicate a condition or state being shared between subroutines.
    • Library System Example: The filled circle between "Validate student information" and "Process books" indicates that a "Valid student information" flag is being passed.

  3. Small Diamond:

    • Meaning: Represents a decision point (optional execution of a subroutine).
    • Usage: Used at the intersection of connecting lines between subroutines that are conditionally called. Alternatively, it may appear on a single connecting line if calling that subroutine is optional.
    • Library System Example: The small diamond between "Returning" and "Check book" shows that checking the book is an optional decision point based on certain conditions.

  4. Curved Arrow:

    • Meaning: Indicates repetition (execution of a subroutine or set of subroutines multiple times).
    • Usage: Shows loops or repeated processes within the system.
    • Library System Example: The curved arrow from "School library system" to "Borrowing" and "Returning" indicates these processes are repeated until the library closes.

Example: Library System Structure Chart

Main Components of the Structure Chart

  1. School Library System:

    • The main control unit of the system.
    • Function: Central control unit managing borrowing and returning processes.
    • Repetition: Executes until the library closes, indicated by a curved arrow looping back to the main system.

  2. Borrowing:

    • Validate Student Information:
      • Receives Valid student information (indicated by an empty circle).
      • Uses a flag (filled circle) to indicate the validity of student information.
    • Book Information:
      • Receives Book ID as a parameter (empty circle).
    • Process Books:
      • Controlled by a decision (small diamond), (curved arrow) indicating it processes until there are no more books.
      • Receives Student ID and Book available flag as inputs.
    • Update Book and Student Files:
      • Receives Book ID and Student ID (empty circles).

  3. Returning:

    • Check Book:
      • Uses a flag (filled circle) for Overdue flag.
      • Receives Book details (empty circle).
    • Locate Book Record:
      • Uses Book details as a parameter (empty circle).
    • Check if Overdue:
      • Uses Date due and Overdue flag (empty and filled circles).
    • Update Files:
      • Receives Student details and Book details as parameters (empty circles).
    • Reports:
      • Optionally generates reports based on Student details and Book details (indicated by a decision diamond and empty circles).

Key Features Illustrated

  • Repetition:

    • Indicated by a curved arrow from the main program to Borrowing and Returning, showing these actions are repeated until the library closes.

  • Decision Points:

    • Diamonds show optional execution of certain subroutines, such as Process Books and the Reports generation.

  • Data Movement:

    • Empty circles indicate data parameters passed between subroutines.
    • Filled circles indicate flags or control variables passed between subroutines.

  • Refinement:

    • Lower-level subroutines can be detailed further in separate charts, which is part of the refinement process.

Refinement

Further details for each lower-level subroutine can be provided in separate, more detailed structure charts. This approach, known as refinement, helps in breaking down complex processes into manageable components. For instance, the Return Book subroutine could be further detailed into subroutines like Validate Return, Calculate Fines, and Update Inventory.

Class Diagrams

What Are Class Diagrams?

Class diagrams are a type of diagram used in software engineering to visually represent the structure of a system. They show the system's classes, their attributes (data), methods (functions), and the relationships between these classes.

Components of a Class Diagram

  1. Classes:

    • Class Name: The name of the class.
    • Attributes: Characteristics or properties of the class (e.g., name, age).
    • Methods: Actions or functions that the class can perform (e.g., saveData(), calculateAge()).

  2. Relationships:

    • Inheritance: This shows that one class (child) is derived from another class (parent), inheriting its attributes and methods.
    • Association: This indicates how classes interact with each other, showing relationships and interactions.

  3. Multiplicity:

    • These are numbers that specify how many instances of a class can be associated with instances of another class.
    • Common multiplicity values:
      • 1..1: Exactly one instance.
      • 0..*: Zero or more instances.
      • 1..*: One or more instances.
      • 0..1: Zero or one instance.

Example Breakdown

Let's look at the example class diagram in more detail:

  1. Person Class:

    • Attributes:
      • firstName: Stores the first name as a string.
      • lastName: Stores the last name as a string.
    • Methods:
      • printFullName(): Prints the full name of the person.

  2. Student Class:

    • Inherits from Person, meaning it gets all attributes and methods of Person.
    • Additional Attributes:
      • studentID: An integer for the student’s ID.
      • homeroom: A string for the homeroom name.
    • Additional Methods:
      • enrolClass(): Allows the student to enrol in a class.
    • Relationships:
      • A Student must study at least one Subject (1..*), and a Subject can have zero or more students (0..*).

  3. Parent Class:

    • Inherits from Person.
    • Additional Attributes:
      • occupation: A string for the parent’s job.
      • alumni: A boolean to indicate if they are an alumnus.

  4. Subject Class:

    • Attributes:
      • studentID: Stores subject ID as an integer.
      • subjectName: Stores the name of the subject as a string.
    • Methods:
      • printStudentList(): Prints a list of students enrolled in the subject.
    • Relationships:
      • Subject can have multiple students enrolled (0..*).

Use and Value of Class Diagrams

  1. Organisation:

    • Class diagrams help organise and visualise the structure of a system, making it easier to understand how different parts interact.

  2. Communication:

    • They provide a clear way to communicate the design of a system to stakeholders, including developers, managers, and clients.

  3. Planning:

    • Class diagrams are useful for planning the structure of a system before coding begins. This helps in identifying potential issues early.

  4. Documentation:

    • They serve as part of the system’s documentation, useful for future reference and for new team members to understand the system.

  5. Code Generation:

    • Some development tools can generate code automatically from class diagrams, speeding up the development process.

Simplified Example

Imagine creating a simple school system with the following classes:

  • Person: Stores basic information like firstName and lastName.
  • Student: Inherits from Person and adds studentID and homeroom.
  • Subject: Represents school subjects with subjectID and subjectName.

The class diagram shows:

  • A Student must be enrolled in at least one Subject.
  • A Subject can have many Students.

This visual representation makes it easy to see the relationships and understand how the system should be structured.

✅ What’s Correct

Symbols

  • Empty circles (◯) are correctly used to represent data parameters such as name, health, and combat details.
  • Filled circles (●) are correctly used to represent control flags such as a valid choice or health status.
  • A decision diamond is appropriately placed before branching to either the victory or defeat path.
  • The curved double-headed arrow between display character details, display boss details, and the combat process correctly indicates repetition until a condition is met.

❌ What’s Incorrect or Misleading

Process Naming

  • Some process boxes use UI or screen-based labels (e.g. Welcome Intro, Level 1/2 Story, Display Character Details).
  • These labels should be replaced with action-based, function-style labels using concise, functional naming (e.g. Show Intro, Show Story, Show Stats).

Decomposition

  • The process labelled Combat System is too broad. It should be broken down into smaller, clearer sub-processes such as Compare Stats, Apply Damage, or Check Result.
  • Without this, the internal logic of combat is hidden and lacks clarity for implementation or refinement.

Conditional Flow Placement

  • The loop condition ("until health ≤ 0") is incorrectly placed between two display processes.
  • The loop should instead surround the entire combat process and be linked to an appropriate control flag to indicate continuation or exit.

Game End Process

  • Game Over is shown after both Victory and Defeat, but it is not clearly defined as a distinct process.
  • It should either be merged into a final process like End Game or clearly labelled as a terminal message process if necessary.

Class Diagram - RPG Framework

This class diagram shows how different parts of the RPG framework are structured and related. The Weapon class represents weapons in the game, the Character class represents general characters, and the Boss class represents more powerful characters that inherit from Character. The Game class manages the overall game, including the player and the bosses. Inheritance is shown with solid lines, indicating which classes derive from others, while dashed lines represent associations, indicating how instances of these classes can interact with each other.

Classes and their components

  1. Class: Weapon

    • Attributes:
      • name (str): This is a string that holds the name of the weapon.
      • damage_bonus (int): This is an integer that represents the additional damage the weapon can inflict.
    • No methods

  2. Class: Character

    • Attributes:
      • name (str): The name of the character.
      • health (int): The health points of the character.
      • damage (int): The base damage the character can inflict.
      • weapon (Weapon or None): The weapon the character holds, which can either be an instance of the Weapon class or None if the character has no weapon.  Setting weapon=None in the Character class constructor provides flexibility, simplifies object creation, and ensures the class can handle cases where a weapon is not assigned. It allows characters to be instantiated with or without a weapon, and the methods within the class can manage the presence or absence of a weapon accordingly.
    • Methods:
      • attack(self, enemy): A function that allows the character to attack an enemy.
      • display(self): A function that displays the character’s information.

  3. Class: Boss

    • Attributes:
      • Inherits all attributes from Character.
      • It specifies that the weapon is a specific "boss weapon". Unlike a Character which can have a weapon set to None by default, a Boss is always created with a specific weapon.
    • Methods:
      • Inherits methods from Character.
      • Overrides:
        • attack(self, enemy): This method overrides the attack method from the Character class to add special behaviour for bosses, such as dealing additional damage and using a special attack.
    • Notes:
      • The super().attack(enemy) call is used to invoke the attack method of the Character class before adding the boss-specific behaviour.

  4. Class: Game

    • Attributes:
      • player (Character or None): This holds the player character, which is an instance of the Character class or None if no player is set.
      • bosses (list of Boss): This is a list that contains multiple Boss objects.
    • Methods:
      • show_intro(self): Displays the game introduction.
      • setup_game(self, name): Sets up the game with the player’s character name.
      • choose_weapon(self): Allows the player to choose a weapon.
      • get_input(self, prompt, options): Handles user input.
      • combat(self, player, enemy): Manages combat between the player and an enemy.
      • display_combat_status(self, player, enemy): Displays the status during combat.
      • handle_boss_battles(self): Manages the sequence of battles with bosses.
      • introduce_boss(self, boss): Introduces each boss.
      • print_victory_message(self, enemy): Prints a victory message after defeating an enemy.
      • print_defeat_message(self, enemy): Prints a defeat message if the player is defeated.
      • end_game(self, is_victory): Ends the game with a win or loss message.
      • run(self): Starts the game.

Relationships between classes

  1. Inheritance:

    • Represented by solid lines with arrows.
    • Boss Inherits from Character: This means that Boss is a specialized form of Character and inherits its attributes and methods. The Boss class can also override methods to change their behaviour.

  2. Association:

    • Represented by dashed lines.
    • Character and Weapon:
      • A Character can have an optional relationship with a Weapon, meaning a character can either have a weapon or none.
      • The multiplicity is 0..1, indicating that a character can have zero or one weapon.
    • Game and Character/Boss:
      • The Game class has a player attribute that references a Character.
      • The Game class has a bosses attribute that is a list of Boss objects, meaning a game can have one or more bosses.
      • The multiplicity for bosses is 1..*, indicating that there is at least one boss.

Illustrating Key Concepts

  • Inheritance and Method Overriding:

  • Polymorphism:

    • The attack method in Character is designed to be overridden by subclasses like Boss. This allows different types of characters (regular Character and Boss) to implement their own version of attack while sharing the same method signature. This is a key aspect of polymorphism where the same method can behave differently based on the object calling it.
